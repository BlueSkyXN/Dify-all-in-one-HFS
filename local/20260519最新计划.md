# 20260519 最新计划：dify-all-in-one 下一步推进

## 1. 当前判断

当前 `local/项目能力地图-2026-05-19/项目能力表.xlsx` 可以作为阅读版能力地图使用，但它不是完成清单。

截至本计划：

- L1 能力域：8 个
- L2 功能组或模块：32 个
- L3 功能点：82 个
- `已开发`：51 个
- `待验证`：20 个
- `已规划`：8 个
- `已设计`：2 个
- `未发现证据`：1 个
- `可运行`：0 个

关键结论：下一步不要优先扩新功能，而是先把“代码已经存在”的能力推进到“有运行证据”。只有完成本地或 Hugging Face live smoke 后，才把能力表中的相关项从 `待验证` 或 `已开发` 升级为 `可运行`。

## 2. 推进原则

1. `已开发` 不等于 `可运行`。代码、配置、文档存在只能说明实现已经落地，不能说明当前镜像、本地容器或线上 Space 已经跑通。
2. `local/` 材料、git log 和 docs 可以作为规划和推断依据，但不能把规划项写成已完成事实。
3. runtime 文件优先于文档。若 `docker/dify.env.runtime`、`Dockerfile`、`docker/nginx.conf` 与 docs 不一致，以 runtime 为准，再修文档。
4. 先验证交付闭环，再做增强。当前最缺的是 build/run/smoke、HF runtime sha、Admin/File 场景、bucket 演练和发布验收证据。
5. 不把 Web terminal 当作已经完成。当前 `/_admin/terminal/` 只有 placeholder；是否引入真实 terminal binary 需要单独决策。

## 3. P0：补运行证据闭环

目标：把当前项目从“代码已实现”推进到“本地和线上可证明运行”。

### 3.1 本地最小闭环

按顺序执行：

```bash
bash -n \
  docker/entrypoint.sh \
  docker/with-dify-env \
  docker/with-plugin-env \
  docker/with-sandbox-env \
  docker/wait-for-core \
  docker/healthcheck.sh \
  scripts/build.sh \
  scripts/run-demo.sh \
  scripts/hf-space-smoke.sh
python3 -m py_compile docker/ops_service.py docker/admin_service.py
git diff --check
scripts/build.sh
scripts/run-demo.sh
OPS_TOKEN=dify_ops_demo_token scripts/hf-space-smoke.sh http://localhost:8080
```

验收证据：

- Docker image build 成功。
- 本地容器启动成功。
- `web-root`、`nginx-health`、`ops-healthz`、`admin-disabled`、`setup-api`、`init-api`、`ops-health`、`ops-system`、`ops-metrics`、`ops-errors` smoke 通过。
- 容器内 `supervisorctl` 能看到关键进程处于 `RUNNING` 或符合预期状态。

完成后更新能力表：

- 本地构建与运行入口相关 L3 可升级为 `可运行`。
- `/healthz`、Docker `HEALTHCHECK`、默认 smoke 覆盖公开路径等条目可根据结果升级。
- 若失败，保留 `待验证`，并把失败 endpoint、日志和下一步写回备注。

### 3.2 Hugging Face live 闭环

本地闭环通过后，再做线上验证：

```bash
hf spaces info BlueSkyXN/dify-all-in-one
OPS_TOKEN=dify_ops_demo_token \
  scripts/hf-space-smoke.sh https://blueskyxn-dify-all-in-one.hf.space
```

验收证据：

- `runtime.raw.sha=<expected commit sha>`。
- 线上 smoke 通过。

完成后更新能力表：

- `runtime.raw.sha` 回读、online smoke 输出记录、`/_ops/errors` 发布门禁等 L3 可按结果升级。
- 若 Space 顶层 `sha` 更新但 `runtime.raw.sha` 未切换，不算完成。

## 5. P1：验证 Admin 与 File Manager

目标：把 Admin/File 从“代码存在”推进到“场景可证明”。

### 5.1 Admin 默认关闭

验证：

```bash
curl -i http://localhost:8080/_admin/
```

预期：

- `ADMIN_ENABLED=false` 时返回 404。
- 不复用 `OPS_TOKEN`。

### 5.2 Admin 开启与 action catalog

验证：

```bash
SMOKE_ADMIN_ENABLED=true \
ADMIN_TOKEN=dify_admin_demo_token \
OPS_TOKEN=dify_ops_demo_token \
scripts/hf-space-smoke.sh http://localhost:8080
```

如需验证写 action：

```bash
SMOKE_ADMIN_ENABLED=true \
SMOKE_ADMIN_ACTIONS=true \
ADMIN_TOKEN=dify_admin_demo_token \
OPS_TOKEN=dify_ops_demo_token \
scripts/hf-space-smoke.sh http://localhost:8080
```

预期：

- `/_admin/api/status` 可访问。
- `/_admin/api/actions` 只列白名单 action。
- `run-health-checks` 需要 `confirm=true` 和 CSRF header。
- action 写入 `ADMIN_AUDIT_LOG`。

### 5.3 File Manager 安全边界

需要补充或扩展 smoke，覆盖：

- `ADMIN_FILES_ENABLED=false` 时 files API 不可用。
- `ADMIN_FILES_ENABLED=true` 且 `ADMIN_FILES_WRITE_ENABLED=false` 时只读可用、写入拒绝。
- `ADMIN_FILES_WRITE_ENABLED=true` 时只允许在 `ADMIN_FILES_ROOT` 内写入。
- `generated.env`、`*.pem`、`*.key`、`*secret*`、`*token*` 等敏感路径拒绝读取或写入。
- symlink 跳出 `ADMIN_FILES_ROOT` 时拒绝。

完成后更新能力表：

- `白名单管理 action`、`文件浏览/文本/上传/改名/删除`、`admin-disabled smoke`、`admin-enabled action smoke`、`file manager 安全边界 smoke` 根据实测结果升级。

## 6. P1：bucket 持久化演练

目标：验证 `/persist`、fallback 和 dump restore，不只停留在代码推断。

需要验证三组场景：

1. `/persist/postgres` 能否作为 live PGDATA 稳定启动。
2. bucket PGDATA 失败时，`POSTGRES_BUCKET_FAILURE_MODE=fallback-to-runtime` 是否正确切换到 `${RUNTIME_ROOT}/postgres`。
3. fallback PGDATA 为空且存在 `/persist/postgres-backups/latest.sql.gz` 时，是否能从 dump 恢复。

注意事项：

- 不要在没有明确确认时执行 `docker volume rm dify-hf-demo-data`。
- 如需破坏性场景，先用新的临时 volume 或独立 HF 测试 Space。
- 记录每次演练的 env、commit sha、容器日志关键行、`/_ops/health` 和 `/_ops/errors`。

完成后更新能力表：

- `/persist live PGDATA 实测`、`fallback-to-runtime 演练`、`dump restore 演练` 根据结果升级。
- 如果只完成本地演练，备注必须写清“本地验证”，不能写成 Hugging Face bucket 已验证。

## 7. P2：Web terminal 决策

当前事实：

- `/_admin/terminal/` 路由存在。
- `docker/webssh_entrypoint.sh` 支持 placeholder。
- 镜像当前没有安装 `ttyd`。
- 因此真实交互式 terminal 不是已完成功能。

建议先做决策，而不是直接实现：

### 方案 A：继续保持 placeholder

适合当前 demo 阶段。

动作：

- 文档明确“当前不提供真实 interactive terminal”。
- 能力表保持 `真实交互式 terminal = 未发现证据`。
- `terminal binary 集成决策` 和 `terminal session/audit/smoke` 保持 `已规划`。

### 方案 B：引入真实 terminal

只有确实需要 break-glass debug 时再做。

最低要求：

- `ttyd` 或同类 binary 的安装和版本固定。
- `/_admin/terminal/` 必须通过 admin auth。
- 默认关闭。
- 只允许 Private/Protected Space 或受控演示环境使用。
- 记录 session open/close audit。
- 补 WebSocket smoke 和安全文档。

## 8. P2：`/_ops` 增强

等 P0/P1 完成后，再做只读增强。

候选项：

1. `/_ops/logs` 增加 service、severity、keyword 过滤。
2. `/_ops/version` 增加 build/runtime SHA 漂移提示。
3. `/_ops` 增加 Plugin Daemon 必需表只读检查。
4. `/healthz` 或 `/_ops/health` 区分 warmup 和真正失败。

边界：

- 仍然保持 `/_ops` 只读。
- 不在 `/_ops` 中加入 restart、SQL、migration、cache clear、任意 shell command。
- 任何写操作继续放到 `/_admin/*`，并使用独立 `ADMIN_TOKEN`、白名单 action、CSRF、confirm 和 audit。

4. 验证 Admin disabled/enabled/action。
5. 扩展并验证 File Manager 安全边界。

## 10. 下一轮更新能力表的规则

更新能力表时按以下规则：

- 有代码但没跑过：保持 `已开发`。
- 有代码且脚本存在，但没跑过当前版本：保持 `待验证`。
- 本地容器跑通：备注写“本地验证通过”，可按范围升级到 `可运行`。
- HF live 跑通且 `runtime.raw.sha` 匹配：备注写“HF live 验证通过”，可升级到 `可运行`。
- 只来自 `local/` 计划或 runbook 后续方向：保持 `已规划`。
- 只有推断来源：备注必须带 `[推断]`。
- terminal placeholder 不能写成真实 terminal 已完成。
